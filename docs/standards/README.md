# Project Standards

Project Standards document **how** contributors are expected to work within the RPG Engine project.

A Standard should answer the following questions:

- Why does this standard exist?
- Where does this standard apply?
- What rules or expectations should contributors follow?
- Why were these rules chosen?
- Are there any approved exceptions?
- Where can contributors find related information?

Standards should describe **current project expectations**, not historical architectural decisions.

Standards are considered **living documents**. Unlike Architectural Decision Records, standards should be updated as the project's practices evolve rather than replaced with new documents.

Avoid duplicating information that already has a single authoritative source elsewhere in the project. Reference or link to that source instead using the appropriate section (for example, Related Documentation or References) when applicable.

Examples of appropriate Standards include:

- Build Configuration
- Coding Style
- Conventional Commits
- Dependency Management
- Documentation Guidelines
- Naming Conventions
- Pull Request Guidelines
- Testing Standards

Examples that generally do **not** require their own Standard include:

- Individual feature documentation
- Temporary development notes
- One-time migration instructions
- Release notes
- Personal development preferences

# Document Maintenance

| Principle | Description |
| ---------- | ----------- |
| **Living Document** | Standards are expected to evolve as the project evolves. |
| **Single Source of Truth** | Avoid duplicating information maintained elsewhere. |
| **Consistency** | Similar standards should follow a consistent structure and terminology. |
| **Clarity** | Standards should emphasize clear expectations over exhaustive detail. |
| **Maintainability** | Update existing standards as practices change instead of creating replacement documents. |
